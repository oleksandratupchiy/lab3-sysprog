# Нотатки для очного захисту

**Що реалізовано?** Навчальна підмножина C: `int main`, цілі змінні, арифметика, логіка, блоки, if/else, while, return, два формати printf. Це не повна граматика ISO C. Приклад для демонстрації — `examples/complex.c`: stdout `-2`, `35`; return 35.

**Токен і правило граматики — у чому різниця?** Лексер перетворює символи на токени з типом, значенням і координатами. `int x=2;` дає INT ID ASSIGN NUMBER SEMI. Термі­нали — типи токенів, нетермінали — `program`, `block`, `statement`, `expression`. Контекстно-вільне правило має один нетермінал зліва, наприклад `expression → expression PLUS expression`. Оголошеність змінної вже залежить від контексту й перевіряється семантичним аналізом.

**Як працює PLY Lex?** `ply.lex.lex(module=self)` збирає правила з `Lexer`. Функціональні правила перевіряються в порядку визначення, прості regex-рядки — за спаданням довжини шаблону. Тому коментарі обробляються до `/`, а `<=` — до `<`. Ідентифікатори після розпізнавання звіряються зі словником ключових слів. Лексер оновлює рядки на переносах і всередині коментарів; стовпець обчислюється від останнього переносу.

**Як працює PLY Yacc?** `yacc.yacc(method='LALR', write_tables=False)` будує таблиці ACTION/GOTO з docstring-продукцій у `Parser`. Парсер зсуває термінали (shift) і згортає праві частини правил у нетермінали (reduce), використовуючи стек станів. У семантичній дії `p[0]` — результат продукції; `p[1]`, `p[2]` тощо — значення її складових. Наприклад, правило додавання створює `BinaryOp('+', left, right)`. Парсер створює AST і не виконує програму.

**LR і LALR(1)?** L означає читання зліва направо, R — побудову правого виведення у зворотному порядку. Канонічний LR(1) використовує один lookahead-токен і LR(1)-стани. LALR(1) об'єднує стани з однаковим LR(0)-ядром, поєднуючи множини lookahead. Таблиці компактніші; деякі LR(1)-граматики після об'єднання отримають конфлікти. PLY застосовує LALR-генерацію таблиць, а не рекурсивний спуск.

**Shift/reduce і reduce/reduce?** Перший — коли можна або зсунути токен, або згорнути правило. Другий — коли можливі два різні згортання. Наприклад, `A → ID` та `B → ID` у тому самому контексті можуть створити reduce/reduce; розв'язання — уточнити граматику, щоб ролі відрізнялися. Автоматичний вибір першого правила не є поясненням правильності.

**Приклад конфлікту арифметики та його розв'язання.** Після `2 + 3` перед `*` неоднозначна граматика `E → E+E | E*E | NUMBER` дозволяє reduce додавання або shift множення. Вищий пріоритет TIMES змушує shift: AST відповідає `2 + (3 * 4)`. Однаковий пріоритет і `left` дають `(7-3)-2`; унарні оператори мають найвищий пріоритет і `right`. У C порівняння `<` мають вищий пріоритет, ніж `==`; далі йдуть `&&`, `||`.

**Dangling else.** У `if(a) if(b) S; else T;` else належить внутрішньому if. Короткому правилу if задано `%prec IF_WITHOUT_ELSE`, який нижчий за ELSE. Парсер обирає shift ELSE і продовжує внутрішній if замість передчасного reduce. Це свідоме розв'язання неоднозначності пріоритетом.

**Як перевірено конфлікти?** Команда `python main.py examples/complex.c --parser-report output/parser.out` вмикає справжній PLY debug-звіт. Він містить граматику, LALR-стани та дії. Невирішених shift/reduce і reduce/reduce конфліктів у поточній граматиці не виявлено; автоматичний тест перевіряє це. Рядки з `!` — відкинуті альтернативні дії, зокрема розв'язані заданими пріоритетами; це не невирішені попередження. Звіт генерується на вимогу, у корені таблиці не записуються. Звичайний режим не приховує warning через NullLogger.

**AST проти дерева розбору?** Дерево розбору містить усі продукції, дужки, розділювачі. AST залишає суттєві конструкції: Program, Block, Declaration, Assignment, BinaryOp тощо. Дужки впливають на структуру, але не потребують окремого AST-вузла. Dataclass-поля утворюють типізовані зв'язки; рядок і стовпець потрібні для помилок.

**Області видимості й таблиці символів.** `SemanticAnalyzer` підтримує стек словників. Блок додає словник; оголошення отримує унікальний символ `v_номер_ім'я`; використання шукається від внутрішньої області назовні. Зв'язування зберігається окремо за ідентичністю AST-вузла, не додаючи службових полів до JSON. Повторне оголошення в одному словнику заборонене. Зовнішню змінну можна затінювати. Невідомі імена перевіряються навіть у недосяжній гілці.

**Чому ініціалізація перевіряється динамічно?** `int x; if(condition) x=1; return x;` залежить від виконаної гілки. Значення None позначає відсутність ініціалізації; читання породжує помилку. Імена вже статично зв'язані, тому плаский словник значень інтерпретатора з унікальними символами зберігає лексичну семантику. При кожному виконанні оголошення значення скидається; це важливо в циклах і для `int x=x;`.

**Інтерпретація проти трансляції.** Інтерпретатор обходить AST і виконує вузли. Генератор обходить той самий AST, але записує Python-оператори. Унікальні імена зберігають затінення попри відсутність блокової області в Python. Декларація генерує `name=None` і потім ініціалізатор; кожне читання проходить через helper. Return стає Python return, а в інтерпретаторі приватний сигнал `_Return` переносить значення через вкладені блоки/цикли.

**Де C відрізняється від Python?** `//` округлює вниз; тут потрібне ділення до нуля, тому обчислюємо `abs(a)//abs(b)` і відновлюємо знак. Remainder — `a - quotient*b`. Python and/or повертають операнди; генератор використовує `int(bool(a) and/or bool(b))`, зберігаючи коротке замикання та результат 0/1. Порівняння і ! теж нормалізуються. None ніколи не є значенням C int.

**Ліміт виконання.** Кожен оператор і кожна перевірка while збільшують лічильник. Після перевищення налаштованого ліміту виникає помилка з координатами. Генератор додає аналогічні tick/guard, щоб автономний файл теж не зациклювався без обмеження. Це не захист від усіх ресурсних витрат.

**Як працює графіка?** `ast_serializer` формує `type`, `label`, `role`, координати, `children` та ID зі шляху до вузла. Навіть однакові літерали-сусіди отримують різні ID. Браузер читає локальний JSON, `d3.hierarchy` будує ієрархію, `d3.tree` обчислює координати, SVG показує вузли й ребра. `d3.zoom` змінює transform; згортання тимчасово переносить дочірні вузли в hidden. Обробники Enter забезпечують керування клавіатурою. Текст виводиться через `.text`, а не HTML.

**Що показати викладачу?** Запустити pytest; `complex.c --tokens`, `--ast`, `--run`; згенерувати Python і виконати його; експортувати JSON і завантажити у сторінку; показати повідомлення для `return missing;`, `int x; return x;`, `return 1/0;`, `while(1);` з малим лімітом. Детальні команди — у README. Відео й слайди не готуються.

**Що доводять тести?** 30 тестів перевіряють конкретні очікування та диференційну еквівалентність успішних програм. Вони не доводять повну ISO C-сумісність чи відсутність усіх помилок; непідтримувані конструкції й ресурсні межі вказані в README.
